# Report: web team (sandbox-web), run 3

Run branch: `fab0/3/report` (head `fdc0f0e`), tasks T1, T2 and T3 merged. `npm test` on that branch: 81 tests, 81 pass. Nothing was run in a real browser or against the running service. The tests use a fake API and a small stand-in for the page elements.

## Delivered

The web area is the checkout step. D8, D9, D10 (service side) and D11 belong to the service and are not reported here.

- **D1** (enter card details and submit for the order's amount): `checkout.html` has a card form with cardholder name, card number, expiry month and year, and security code. The order, amount (minor units) and currency come from the address, `checkout.html?order=…&amount=2599&currency=USD`, read by `parseOrderParams` in `src/checkout.js`. An incomplete link shows a message and no form. `index.html` builds such a link for a test checkout. The page loads Order payment status first and shows the form only when the order is not paid. The submit goes through `payOrder` in `src/payments-api.js` (POST /payments, a fresh Idempotency-Key per submit).
- **D2** (success shows paid and the amount charged): on `succeeded` the page shows "This order is paid" with the amount charged and the card brand and last four digits (`showPaid` in `src/checkout.js`; panel `paid-panel` in `checkout.html`). The amount is taken from the returned payment, not from the link. Tests: "a successful payment shows paid and the amount charged (D2)" and "page: success shows paid with the amount charged".
- **D3** (decline shown with a plain reason): on `declined` the page shows "The payment did not go through" and the service's `message` as it is, with the reason code set as `data-reason` on the panel for styling. Nothing is hard-coded per reason. A test covers each of the five reason codes.
- **D4** (invalid details rejected before any payment, with the wrong field named): `validateCard` in `src/card-validation.js` checks required fields, 12 to 19 digit number with Luhn check, expiry not in the past (UTC month), and security code length by brand (4 for amex, 3 otherwise). The submit stops with an error under each wrong field, and nothing is sent. When the service answers `validation_failed`, its field messages are shown next to the same fields. The names `cardholder_name`, `number`, `expiry` and `security_code` and the codes are the same locally and in the service. Tests: `tests/card-validation.test.js` (24) and the D4 tests in `tests/checkout.test.js`.
- **D5** (retry on the same page): after a decline the form stays on the page with the order kept, the number and code cleared, and the focus on the number. The next submit gets a new Idempotency-Key, so it is a new attempt. A later success shows the order as paid. Test: "after a decline the customer retries with the same order and a later success marks it paid (D5)".
- **D6** (paid order cannot be paid again): a paid order shows as paid on load, with no form. If Pay order answers `order_already_paid` (409), the page shows the order as paid together with the service's message and no form, and it rereads the status to show the amount charged. Tests for both cases are in `tests/checkout.test.js`.
- **D7** (no second submit while processing): `submit()` takes a lock before its first await, so a double click in the same tick makes one call. While processing, the form fieldset and the Pay button are disabled and the button reads "Processing payment…". The page also sends an Idempotency-Key as the contract asks. Tests: "a double click makes one payment attempt (D7)" and "the form is locked from the moment of submit until the answer (D7)".
- **Contract client** (`src/payments-api.js`, `src/config.js`): tells apart `succeeded`, `declined`, `refused` (with `fields` and `fieldErrors`) and `error` (network failure, 500, unreadable answer). The base URL is kept in one place, default `http://127.0.0.1:8000`, and can be changed with `window.CHECKOUT_CONFIG.paymentsBaseUrl` or `setPaymentsBaseUrl()`. Requests use `credentials: 'omit'`.
- **D10, web side** (card data on the page): the full number and the security code are read from the form only inside `submit()`, sent in the one POST, and cleared from the form after every attempt that was sent. They are not kept in page state, storage or the URL, and not logged. Returned payments are copied field by field, so only brand and last four digits remain. Tests assert that no state given to the view contains them.
- **Failure handling**: after a failure with no usable answer (no connection, 500), the page reads the order's status before it offers the form again. A payment that did go through then shows as paid, as the contract advises.
- **Docs**: `README.md` describes the link format, behaviour, how to run it (`python3 -m http.server 8080` next to the service on port 8000) and `npm test`, and points to the service's `docs/test-cards.md`.

## Deviations

None from the spec or the contract.

Choices the contract left to the checkout, so that they can be checked:
- The page does not resend a failed Pay order with the same Idempotency-Key. It reads the order status instead. The contract allows this: it says to reuse the key when resending, and to read the order's status before submitting again after a 500.
- The amount and currency come from the page address and are sent as given, as in the spec's reading of open question 2. A currency in lower case is turned to upper case.
- When the checkout cannot read an already-paid order's payment, the "Amount charged" row is left out rather than showing the amount from the link.

## Open questions

- Not run end to end. The pages and the client were not run in a browser or against the running service, so the cross-origin calls (CORS headers, the `Idempotency-Replayed` header) and the live answers are untested here. A manual run with `python3 -m http.server 8080`, the service on port 8000 and the test cards would settle this.
- Where the order and amount come from. The checkout takes them from the address of the page, because no order or cart exists in this Story. Anyone can edit the address, and the service does not check the amount (spec open question 2). It would settle when orders exist on the service or in the checkout that links here.
- The wording of the local validation messages is written by this team. The service's own messages may differ in wording for the same field. This is only visible when both are shown for the same input. The product owner can confirm the wording, or the checkout can later show only the service's messages.
