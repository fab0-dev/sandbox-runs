# Feedback: sandbox-api, run 8

Report on the service team's part (sandbox-api), read on `origin/sandbox-api/8/base` (merge of implement-T1 to T3, `3c5293a`) against `main` (`ce3f377`). The full suite (`python3 -m unittest discover -s tests -t .`) ran on that commit: 243 tests, all pass.

## Delivered

Spec statements in the service's area. D13 to D16 belong to the web team and are not reported here.

- **D1, refund a succeeded payment.** `POST /payments/{payment_reference}/refund` with `{"reason": ...}` answers 200 with `{"payment": {...}}`. The payment keeps outcome `succeeded` and carries `refund: {amount, currency, reason, refunded_at}`. Amount and currency are copied from the payment's own row inside the same SQL statement that writes the refund; the reason is kept as given; the time is UTC with a trailing Z. In `payments/store.py` (`PaymentStore.refund_payment`, `refunds` table), `payments/service.py` (`PaymentService.refund_payment`) and `payments/api.py` (`_refund_payment`, `_REFUND_PATH`).
- **D2, missing or blank reason.** Refused as `reason_required` (422): missing, null, not text, empty, whitespace only, or no body at all. Nothing is written. A reason over 500 characters is refused as `reason_too_long` (422); the spec left the limit to the service (open question 4). A body that is not valid JSON or not an object is `invalid_request` (400). `payments/service.py`, `payments/api.py`.
- **D3 to D6, the refusals.** `payment_not_found` (404), `payment_declined` (409, says it took no money), `payment_already_refunded` (409, message and `refunded_at` give the first refund's time; the first refund is untouched). Each has its own code and a plain-words message in the standard error body, and a success carries `payment` with no `error`. Checks run in the order reason, not found, declined, already refunded. `payments/service.py`, `payments/api.py` (`STATUS_BY_CODE`).
- **D7, simultaneous refunds.** Three layers: the refund runs under the order's lock (the same one pay uses); the `refunds` table has the payment reference as primary key; and the check and the write are one statement. Tests: `test_two_simultaneous_refunds_give_one_success_and_one_already_refunded` and `test_many_simultaneous_refunds_give_exactly_one_success` in `tests/test_service.py`; `test_two_simultaneous_refunds_give_one_200_and_one_already_refunded` in `tests/test_api.py`; store-level tests in `tests/test_store.py`. Triggers on `refunds` also refuse a refund that does not match a succeeded payment's amount and currency, and any update or delete of a refund.
- **D8, Order payment status.** The answer is now `{order_reference, status, paid, refunded_at, payments}`. `status` is `unpaid`, `paid` or `refunded`; `refunded_at` is the refund's time for a refunded order, else null; the refund shows on the succeeded payment among the attempts. `paid` is kept and is true only for `paid` (false for a refunded order). Unpaid and paid orders give the same answer as before plus `status` and `refunded_at: null`. `payments/service.py` (`OrderStatus`, `order_status`).
- **D9, List payments.** Every payment read from the store (by order, by list, by reference) carries `refund` (null or the object) through a LEFT JOIN. Order, paging and `outcome` narrowing are unchanged. `payments/store.py`.
- **D10, paying a refunded order.** Pay order refuses with `order_refunded` (409), message "This order was refunded, so it cannot be paid again.", plus `order_reference` and `refunded_at`. The check runs under the order's lock, before any attempt, so no payment is tried and nothing is recorded. It is judged after `idempotency_key_reused` and before `order_already_paid`. `payments/service.py` (`_attempt`).
- **D11, no card data.** A refund holds only amount, currency, reason and time. Tests that check refund answers, refusals and stored rows for card number and security code: `test_nothing_returned_or_stored_about_a_refund_holds_card_data` and `test_a_refusal_holds_no_card_data` in `tests/test_service.py`, `test_the_answers_hold_no_card_data` in `tests/test_api.py`.
- **D12, documentation.** `docs/refunds.md` gives the request, the reason rules, the answer, each refusal with HTTP status, code and message, the refused payment of a refunded order, and step-by-step commands with the test cards for D1 to D5 and D10. The README links it, lists the new route and the new codes, and describes the changed status answer. `tests/test_docs.py` checks that every refund-related code the service can return appears in the document. The T3 author ran the commands against a live service and got 200, 422 (twice), 404, 409, 409 and 409 for D1, D2, D3, D4, D5 and D10.
- **Cross-origin.** The CORS headers are on every answer of the new route, and OPTIONS on `/payments/{payment_reference}/refund` answers the preflight 204. A method other than POST there gives 405 with `Allow: POST, OPTIONS`. `payments/api.py`.
- **D17, service suite.** The earlier Stories' cases (paying, declines, retry, already paid, double submit, replay, list, lookup) pass unchanged on the merged branch: 243 tests, OK. One existing expectation in `tests/test_api.py` (`test_success_is_201_with_the_payment`) was updated to include `"refund": None`, as the contract's payment shape requires. The web team's suite is not covered here.

## Deviations

None from the spec or from the contract (`runs/sandbox-api/8/contract.yaml`). The code's routes, statuses, codes, messages, check order and members match it where compared. Choices the contract left to the service were made as it states them: the 500-character reason limit, the refund taking the payment (not the order), and `paid` kept but false for a refunded order.

## Open questions

- **A replay of a success after a refund shows the old payment.** A repeated `Idempotency-Key` with the same body is replayed before the refunded check (the contract says so). So a stale checkout that resends a successful submit gets 200 with `refund: null` on the payment, even if the order was refunded in between. The contract documents this and tells readers to use Order payment status. The spec does not settle whether the checkout needs more than that; the web run record would show whether it matters.
- **Burst size over HTTP.** `ThreadingHTTPServer` has a listen backlog of 5. The HTTP-level concurrent refund test uses 5 simultaneous connections (an earlier attempt used 6 and failed 4 times in 20 runs). D7 is proven with more requests at service level (8 and 12 threads, no sockets). A burst of more than 5 at once over HTTP can see connection errors; this is not a refund rule and would need a change to the server setup to settle.
- **Access control.** Refund payment has no authentication, as the spec's open question 7 accepts. It is left to the authentication Story.
