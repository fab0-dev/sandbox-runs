# Report: service team (sandbox-api), run 3, attempt 1

Read: the spec, the task list (T1 to T3), `contract.yaml`, and the code on `fab0/3/report` (it equals `fab0/3/implement-T3` plus the merge commits). I ran the suite there: `python3 -m unittest discover -s tests -t .` gives 128 tests, all OK. This report covers the service area only (D4 and D6 to D11, and the service side of D1 to D3, D5 and D7). The web checkout's own parts (the form, showing the result, the disabled submit button) are not reported here.

## Delivered

- **D1 (service side).** Pay order is `POST /payments` and takes the order reference, amount in minor units, currency, and the card (cardholder name, number, expiry month and year, security code). `payments/api.py`, `payments/service.py`. The form itself belongs to web.
- **D2.** A valid card that is approved gives HTTP 201 with `payment.outcome = "succeeded"`, `order_paid: true`, the amount and currency, and a confirmation message. `payments/service.py` (`pay_order`, `_attempt`), `payments/processor.py`.
- **D3.** A decline is a normal 201 answer with `outcome = "declined"`, one of the five reason codes (`card_declined`, `insufficient_funds`, `expired_card`, `incorrect_card_details`, `processing_error`) and a plain-words `message` to show as is. The reason comes from the test card number. `payments/processor.py` (`DECLINE_MESSAGES`, `TEST_CARDS`). The three answers (succeeded, declined, refused) can be told apart by `payment.outcome` versus `error.code`.
- **D4.** Invalid cards are refused before any payment is tried, with 422 `validation_failed`. `error.fields` names every invalid field (`cardholder_name`, `number`, `expiry`, `security_code`) with a code and a customer message. Checked: required fields, 12 to 19 digits, Luhn check digit, expiry in the past (good through the end of the expiry month, UTC), security code length by brand (3 digits, 4 for amex), name not blank and at most 100 characters. `payments/cards.py` (`validate_card`). Also refused without a payment: non-positive or non-integer amount (422 `invalid_amount`) and malformed requests (400 `invalid_request`). Nothing is recorded for a refusal.
- **D5 (service side).** After a decline the order stays unpaid and a new request, with the same or another card, is a new attempt. A later success marks the order paid. `payments/service.py`, `payments/store.py`.
- **D6.** Once an order has a succeeded attempt, a further pay request is refused with 409 `order_already_paid` and a plain message, and no attempt is recorded. The store also has a unique index allowing at most one succeeded attempt per order, as a second guard. `payments/service.py`, `payments/store.py`.
- **D7 (service side).** Attempts are serialised per order (`_OrderLocks`), so simultaneous requests for one order cannot both succeed. A repeated `Idempotency-Key` with the same request returns the first answer (200, `Idempotency-Replayed: true`) without a new attempt. A repeated key with a different request is refused (422 `idempotency_key_reused`). Tests cover the concurrent cases (`tests/test_service.py`, `tests/test_api.py`).
- **D8.** Every attempt, succeeded or declined, is recorded in sqlite3 with payment reference, order, amount (integer minor units), currency, outcome, decline reason, message, card brand, last four digits and UTC time. `payments/store.py` (`record_attempt`).
- **D9.** `GET /payments` lists payments newest first, optionally narrowed with `outcome=succeeded|declined`, paged with `limit` (1 to 500, default 100) and `cursor`. `GET /orders/{order_reference}/payments` gives `paid` and all attempts for the order, newest first. An order with no attempts is answered as unpaid with an empty list. `payments/api.py`, `payments/service.py`, `payments/store.py`.
- **D10.** The store has no column for a full number or a security code and `record_attempt` rejects a `last4` that is not four digits. Responses show only `card.brand` and `card.last4`. Validation and refusal messages are fixed texts. The request log never prints bodies. For the idempotency "same request" check, the service keeps only a keyed HMAC digest computed without the full number and the security code. `payments/store.py`, `payments/cards.py`, `payments/service.py`, `payments/api.py`.
- **D11.** `docs/test-cards.md` lists the test cards for each outcome and each decline reason, with the rule for the other fields. The same list is in `payments/processor.py` (`TEST_CARDS`) and in the contract. Every other Luhn-valid number is approved.
- **Also delivered.** Server entry point `python3 -m payments` with `--host` (127.0.0.1), `--port` (8000) and `--db` (or `PAYMENTS_DB`, default `payments.db`) in `payments/__main__.py`. CORS headers and preflight as the contract says. `README.md` describes running, calls, refusals and the card-data rule. Uses the Python standard library only.

## Deviations

None from the spec's "Done when" statements or its interfaces. Against `contract.yaml`, the following details go beyond or are not stated in it. None changes a name, status code or shape the web team builds against.

- An `Idempotency-Key` that is empty or longer than 255 characters is refused as 400 `invalid_request`. The contract states the 1 to 255 limit but does not list this under `invalid_request`. The README does.
- `order_reference` must be 1 to 255 characters, and an `amount` above 2^63-1 is refused as `invalid_amount`. The contract says only "non-empty" and "greater than 0". The limits come from the store.
- A cardholder name with control characters is refused as `invalid_format`. The contract names only the blank and length rules.
- When the card number is missing or malformed, the brand is unknown, so a security code of 3 or 4 digits is accepted for that check (the number is already reported). The contract says 3 digits, or 4 for amex.
- Remembered idempotency keys are held in memory, at most the last 10,000, so a restart forgets them. The contract does not say whether keys survive a restart. The README says it.
- A request with `Transfer-Encoding`, a bad `Content-Length` or a body over 64 KB is refused as 400 `invalid_request` and the connection is closed. The contract does not set a body limit.

## Open questions

- **Amount against the order.** The service charges the amount the checkout sends and does not check it against an order record (spec open question 2). It would be settled when orders exist on the service.
- **Idempotency keys across a restart.** After a restart a resent key could make a new attempt, though an already-paid order is still refused by the store. It would be settled by a decision whether keys must be stored, which means a stored digest of the request.
- **Access control.** There is no authentication and any origin is allowed, so anyone who can reach the service can list payments. This is for the Story that adds authentication, and the product owner decides when.
- **Shop screen.** The shop sees outcomes only through List payments and Order payment status (spec open question 3). A back-office screen would be a separate Story if wanted.
- **Not checked here.** I ran the test suite on the report branch. I did not start the server myself or call it from a web checkout. How the web team's checkout uses the contract is outside this area.
